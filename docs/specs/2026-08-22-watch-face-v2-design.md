# TokenLink 表盘与协议 v2 设计（草案）

状态：草案（待评审）

日期：2026-08-22

目标平台：M5Stack StopWatch Dev Kit C152 固件 + TokenLink macOS 管控端

## 1. 背景与目标

v0.1 已交付：Mac 端展示 Codex / Kimi / MiniMax / GLM 四家额度，手表沿用
固件 v1 行为（六个匿名会话圆、左键 PTT、右键 Voice Chat、中央 Send、滑动
手势），只接收 Codex primary window 的 v1 payload。

本设计覆盖下一个子项目的两件事：

1. **表盘信息架构与交互**：页面结构、按键映射、状态视觉层级；
2. **协议 v2 字段需求**：由表盘要显示的内容反推 payload，而不是反过来。

设计原则按优先级排序：

- **表盘是"看一眼"的设备**。最高频的交互是 glance，不是按键；任何状态
  都要能在一秒内读出"现在能不能放心跑 agent"。
- **高频动作占最好的键**。按键频率排序：切换查看 > 确认/刷新 > 语音输入。
- **单键单义**。手势学习成本：单击 < 滑动 < 长按 < 双击；不引入组合键，
  每个键最多承载"短按 + 长按"两个语义，且长按语义必须是短按的加强版或
  同族动作。
- **尊重已有肌肉记忆**。左键 PTT、中央 Send 是存量用户已习惯的行为，
  保持不变。
- 不破坏 v1 payload 兼容，不把凭据、账户身份、任务文本下放到固件。

## 2. 用户交互习惯分析

从 v0.1 的使用方式反推动作频率：

| 动作 | 典型频率 | 当前入口 | 评价 |
| --- | --- | --- | --- |
| 看时间 / 看额度还剩多少 | 每天几十次（glance） | 主页 | 已是主页，保持 |
| 切换看另一家 provider / 另一个窗口 | 每天几次到十几次 | 不支持 | v2 核心新增 |
| 确认 agent 会话状态（谁卡住了/谁完成了） | 每天几次 | 六匿名圆 | 可理解性差，需重设计 |
| 手动刷新一次额度 | 偶尔 | 不支持 | 新增，低频 |
| 语音输入（PTT / Voice Chat） | 因人而异，低频到中频 | 左键 / 右键 | 保持 |

结论：按键资源应向"切换查看"倾斜；语音类动作保留但不占据最顺手的
短按导航位。

## 3. 表盘页面结构

页面数量从"一张脸"扩展为四个固定页面，**顺序固定、循环轮转**，不存在
层级菜单——表盘设备上菜单是反模式。

### P0 主页（默认页）

- 时间（保持 StopWatch 的本职）；
- 连接状态点：绿 = 已同步，黄 = stale，灰 = 离线；
- 最紧张额度窗口：大字百分比 + provider 标识（图标或首字母块）+ 窗口
  标签（5h / 周 / 月）+ reset 倒计时一行；
- 有 agent 会话"需要输入"或"完成"时，底部出一条提醒横条（见第 5 节）。

主页回答一个问题：**我现在最缺的是哪家的哪档额度，还能用多久。**

### P1 额度页

- 每个 provider 一行：标识 + 名称缩写 + 最紧张窗口百分比 + 倒计时；
- 上下滑动或中央键在该 provider 的多个窗口间展开切换（5h → 周 → 月）；
- 只显示 Mac 端已启用且有数据的 provider；某家 stale 时该行置灰并显示
  最后同步时间，不显示虚构实时值。

### P2 会话页（替代六个匿名圆）

六个匿名会话圆的问题：占掉表盘三分之一以上的面积，且用户记不住"第几个
圆是哪个任务"。v2 改为**最多三个可命名工作单元**，且不再是 Codex 专属
概念：

- 工作单元 = 一个"agent 会话"的通用抽象，带来源标记（Codex / Kimi /
  其他），协议字段见第 6 节；
- 每个单元显示：短名（Mac 端配置，如 "review"、"fix-ci"）+ 来源标识 +
  状态（运行中 / 需要输入 / 完成 / 失败）+ 最近更新时间；
- 命名在 Mac 管控端完成，手表只显示，不提供编辑；
- 三个而非六个：超出屏幕可读密度，且并行跑三个以上 agent 不是主流场景。
  超出三个时 Mac 端按最近活跃排序取舍，表盘不翻页。

**各厂商会话能力的现实情况**（2026-08 调研）：

- **Codex**：能力最完整。app-server 有会话（thread）列表和回合完成通知，
  Mac 端可以确知"最新完成的会话"，并通过 NSWorkspace / AppleScript 聚焦
  Codex Desktop。**点按聚焦在 v2 只对 Codex 完整支持。**
- **Kimi Code**：CLI 有 `/sessions`、`/title`、`kimi -r` 恢复，且实现了
  ACP 协议（session/new、load 等稳定面 10/12），理论上能提供只读会话状
  态；但会话跑在终端里，"聚焦到那个终端窗口"没有稳定映射，Kimi 网页版
  的浏览器标签聚焦同样脆弱。v2 里 Kimi 工作单元至多做到**只读状态展示，
  不支持点按聚焦**。
- **dsh（DeepSeek Harness）**：Web 形态，会话日志可被插件读取做状态统
  计，但聚焦浏览器标签页不可靠。不进入 v2 工作单元来源。

**点按聚焦交互**：在 P2 页点按某个工作单元（圆形触摸屏直接点条目），
手表经协议 v2 命令通道（第 6 节）发 `focus` 指令给 Mac，Mac 聚焦对应应
用并选中该会话。这是"看一眼 → 点一下 → 回到电脑上继续"的闭环，预计是
会话页最高频的操作。无来源能力的单元点按无动作（置灰提示）。

### P3 系统页

- BLE 连接状态与已绑定 Mac 标识（脱敏后）；
- 上次同步时间与数据新鲜度；
- 固件版本 / 协议版本 / 电量。

## 4. 按键映射

| 输入 | 语义 | 理由 |
| --- | --- | --- |
| 右键短按 | 下一页（P0→P1→P2→P3→P0） | 最高频导航动作用最顺手的键 |
| 右键长按 | 直接回主页 P0 | "回家"是导航的同族加强语义，任何页面一键返回 |
| 左键按住 | PTT（不变） | 存量肌肉记忆 |
| 中央键短按 | 页面主动作：P0=立即刷新额度；P1=展开/收起该 provider 的窗口；P2=确认当前选中会话；P3=立即同步 | "确认/做点什么"的直觉语义，各页含义一致 |
| 中央键长按 | Voice Chat（从右键迁移） | 语音是"按住说话"族的动作，与 PTT 同族；右键让位给更高频的导航 |
| 上下滑动 | 页内滚动 / 条目切换 | 保持现状 |
| 点按屏幕条目 | 选中 / 聚焦（P2 点工作单元 = 聚焦对应 Mac 应用会话） | 全屏触摸是现有能力；点按是触屏最直觉的"我要这个" |
| 中央区点按（P0 主页） | Send（保持现有 HID 映射） | 存量肌肉记忆；其他页面的中央区点按 = 页面主动作，与中央键短按同义 |

设计说明：

- **右键从 Voice Chat 改为翻页**是本设计唯一改变的存量映射。依据是第 2
  节的频率排序：翻页每天发生若干次，Voice Chat 是低频动作；低频动作不
  应占用唯一的短按导航位。中央键长按承接 Voice Chat 后，"两个语音动作
  都是按住说话"，语义反而更一致。
- 中央键短按在各页都是"对当前内容做主操作"，用户不需要记忆四个页面各
  自的键位表。
- 离线 / 未绑定 Mac 时按键行为不变，只是页面内容显示离线状态——不让用
  户在异常时面对一套不同的交互。
- 不引入双击：表盘按键的双击误触率高，且所有语义已被短按/长按覆盖。

## 5. 视觉层级与状态语义

状态色全局统一，四个页面同义：

- 绿：健康 / 已同步；黄：stale（显示最后同步时间）；红：错误或额度告急
  （剩余 <10%）；灰：离线 / 未绑定。

提醒层级（打扰程度递增）：

1. **角标**：会话"完成"在主页底部出一条静态横条，用户下次 glance 自然
   看到；
2. **呼吸闪烁**：会话"需要输入"——这是唯一值得主动吸引注意的状态，
   对应工作单元圆点慢闪烁；
3. **振动**：仅用于 PTT/Voice Chat 的录音开始/结束确认，不用于额度或
   会话提醒——表盘振动留给"用户正在操作设备"的场景。

额度告急不主动振动：额度是渐进消耗的，主页红黄状态已足够；振动提醒会
在长跑任务时造成骚扰。

## 6. 宠物表盘主题（可选，默认关闭）

电子宠物是给"看表"这个动作加情感价值的可选项，不是默认形态：

- **它是一个表盘主题**，不是新模式：在 Mac 管控端开启后替换 P0 主页
  （数据页 P1/P2/P3 保持纯数据不变），默认关闭，随时可关；
- 宠物状态就是系统状态的拟物化映射，不引入独立的养成数值：
  - 精力值 = 当前最紧张窗口的剩余百分比（满额度 = 活蹦乱跳，告急 =
    蔫/趴下）；
  - stale = 打瞌睡（附最后同步时间）；离线 = 钻窝睡觉；
  - 有会话"需要输入" = 跳起并挥手（替代静态横条的提醒位）；
- 交互只有两条：点按宠物 = 立即刷新额度（"喂食"），其余按键语义与数据
  主题完全一致——**主题只换皮，不换交互**，用户切换主题不需要重新学习；
- 美术约束：AMOLED 纯黑背景 + 小型原创像素风角色，8–12 fps 帧动画，
  黑色像素不耗电（见第 8 节）。角色必须原创，不使用 Stack-chan 或任何
  第三方形象资产（同硬件上有 stackchan-idf 的先例，但资产授权不满足
  本项目的 MIT 分发要求）。

## 7. 低功耗与抬腕唤醒

C152 的硬件底子允许认真做功耗（2026-08 核实 [M5Stack 官方规格](https://docs.m5stack.com/en/products/sku/C152)）：

- **BMI270 六轴 IMU**：可穿戴常用芯片，内置手腕手势引擎，其 IMU_INT 经
  M5PM1 的 PYG0 接到 ESP32-S3 的中断唤醒脚（G12_PY_IRQ）——**抬腕唤醒
  在硬件层面是通的**：熄屏状态下 BMI270 低功耗常开，检测到抬腕动作产生
  中断唤醒主控点亮屏幕。
- **M5PM1 分级电源轨**：AMOLED（L3B）、音频、扬声器、马达各自独立门控，
  熄屏时可以只保留主控 + BLE + IMU。
- **RX8130CE RTC**：与 IMU 共用同一根中断唤醒线，可用于定时唤醒同步。
- **AMOLED 特性**：黑色像素不发光不耗电，表盘一律深色底；宠物主题同样
  遵守。
- 电池 450mAh。

功耗档位设计（在现有固件基础上扩展）：

1. **活跃**：屏幕点亮，全功能；
2. **熄屏待机**（现有 desk sleep 的强化版）：关 AMOLED/音频/马达电源轨，
   BLE 保活，IMU 进入手势检测模式——抬腕或点按屏幕即回活跃；
3. **旅行模式**（现有）：PM1 真关机。

抬腕唤醒为可配置项（默认开），另有"仅点按唤醒"选项给对误触敏感的用户。
**注意**：现有固件的 desk sleep/wake 与旅行模式在上游项目里仍标注为
experimental、浸泡测试未完成——v2 实现时功耗档位与抬腕唤醒必须做真机
浸泡验证（连续 24h 以上，记录电量曲线与 BLE 重连率），这是验收项。

## 8. 协议 v2 字段需求（由表盘反推）

表盘要显示什么，协议就传什么，不多传：

```json
{
  "v": 2,
  "provider_id": "codex",
  "windows": [
    {"id": "5h", "remaining_percent": 72, "reset_in_seconds": 900}
  ],
  "work_items": [
    {"slot": 0, "name": "review", "source": "codex", "state": "running"},
    {"slot": 1, "name": "fix-ci", "source": "codex", "state": "needs_input"}
  ],
  "synced_at": 1787616000
}
```

手表 → Mac 方向新增一条**命令通道**（独立于额度 payload 的 GATT
characteristic，绑定链路上写）：

```json
{"action": "focus", "slot": 1}
```

规则：

- **版本协商**：连接后 Mac 与固件交换 capabilities；固件不认 v2 时 Mac
  回退 v1 payload（`remaining_percent` / `reset_in_seconds`），v1 行为
  完全保留。
- `provider_id` 用稳定字符串（与 Mac 端 `ProviderID` 一致）；provider 标
  识用**内置图标表**（固件内置四个图标 + 一个通用问号），不下传位图。
- `windows` 数组最多 3 个窗口（5h/周/月）；`reset_in_seconds` 仍在发送
  时由 Mac 计算并 clamp 到非负。
- `work_items` 最多 3 个；`name` 限 12 个 ASCII 字符（Mac 端截断并校验，
  不接受任务内容、路径或自由文本）；`source` 标记来源 provider；
  `state` 为枚举，固件不做字符串解析。
- `focus` 命令只携带 slot 序号，会话与 Mac 应用的对应关系只存在 Mac 端；
  Mac 收到后聚焦对应应用并选中会话。v2 仅 Codex 来源的工作单元响应
  focus，其他来源的单元在固件侧就不接受点按。
- 多 provider 轮转：Mac 按页面停留逻辑分时发送不同 provider 的 v2
  payload，或在单个 payload 里携带多家窗口数组——实现阶段根据 BLE MTU
  和更新频率实测再定，本设计不锁死。
- 隐私不变：payload 不含凭据、账户标识、prompt、任务文本。

## 9. Mac 端配合（TokenLink v0.2 范围）

- 管控中心新增"表盘"配置区（替换 v0.1 的路线图提示侧栏项）：
  - 选择同步哪些 provider 到手表（默认仍只有 Codex）；
  - 工作单元命名与管理（最多三个）；
  - 表盘主题：数据 / 宠物（默认数据）；
  - 唤醒方式：抬腕唤醒（默认开）/ 仅点按唤醒；
  - 表盘偏好：12/24 小时制、语言（跟随 app 设置）。
- 会话聚焦的 Mac 侧实现：Codex 工作单元记录 thread 标识，收到 `focus`
  命令后聚焦 Codex Desktop 并选中对应会话（具体 app-server 方法在实现
  阶段验证）。
- v2 payload 预览：在 StopWatch 页显示当前实际发送的 JSON（脱敏后），
  便于调试固件。

## 10. 验证清单

1. 固件模拟器：四页面轮转、按键与触摸映射、状态色、v1/v2 协商与回退；
2. BLE 协议测试：v2 payload 编解码、超长 name 截断、未知字段忽略、
   focus 命令、降级到 v1；
3. C152 真机：按键手感与误触率、glance 可读性（一臂距离、户外亮度）、
   PTT 与 Voice Chat 回归、点按聚焦闭环；
4. 功耗浸泡（验收项）：熄屏待机 / 抬腕唤醒连续 24h+，记录电量曲线、
   抬腕识别率与 BLE 重连率；
5. Mac 端：多 provider 同步策略、工作单元命名、Codex 会话聚焦、协议
   版本展示。

## 11. 明确不做

- 不下传 logo 位图或自定义图片（内置图标表足够，且避免资产授权问题）；
  宠物形象为原创像素资产，不引入第三方形象；
- 不做表盘上的文字输入（命名一律在 Mac 端）；
- 不做表盘商店、第三方表盘；
- 不引入双击或组合键；
- 不为额度变化做振动提醒；
- 宠物主题不做养成/喂食数值体系，它只是系统状态的拟物化皮肤；
- Kimi / dsh 的会话聚焦在 v2 不做（能力不存在或不可靠，见第 3 节）。
